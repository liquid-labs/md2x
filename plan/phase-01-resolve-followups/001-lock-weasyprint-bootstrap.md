# Lock Cold WeasyPrint Bootstrap Against Concurrent Races

## Purpose and scope

Closes followup `AOJw`. `src/cli/lib/ensure-weasyprint.sh`'s `ensure-weasyprint()` function gates the entire cold-bootstrap sequence (`python3 -m venv`, `ensurepip`, `pip install weasyprint==69.0`) behind a single unlocked `[[ -x "${WEASYPRINT_BIN}" ]]` existence check. If two `md2x` processes both hit a cold start at once (first-ever PDF conversion on a machine, kicked off twice concurrently), both see the check fail and both start building `${VENV_DIR}` (`~/.md2x/venv`) at the same time — their `venv`/`ensurepip`/`pip install` steps can interleave and corrupt the shared directory. Add a locking (or atomic staging-dir+rename) mechanism to `src/cli/lib/ensure-weasyprint.sh` that closes this race, written in the repo's existing plain bash style (no new external tool dependency — see the `flock`-availability note under Requirements).

This is a scoped bugfix to one file's concurrency behavior; no CLI flag, output format, or documented behavior changes as a result. Read `src/cli/lib/ensure-weasyprint.sh` and `src/cli/md2x.sh` (specifically the `ensure-weasyprint` call site at line 116, and the CSS-temp-file `trap ... EXIT` registration at lines ~216-235, which runs *after* `ensure-weasyprint` and which the fix here must not be clobbered by or clobber) before starting.

## Requirements

- Add a mutual-exclusion mechanism around the cold-bootstrap body of `ensure-weasyprint()` (the `python3 -m venv` / `ensurepip` / `pip install` sequence) so that two concurrent invocations never run those steps against the same `${VENV_DIR}` at the same time.
  - Prefer a portable `mkdir`-based lock directory (`mkdir` is atomic on POSIX filesystems and needs no external dependency) over `flock`: `flock` is a Linux (util-linux) tool not reliably present on macOS, and this repo's test/dev environment is macOS (see `AGENTS.md`'s Homebrew note) — don't introduce a dependency the preflight check doesn't already verify. An atomic staging-dir + rename approach (build the venv at a throwaway path, then `mv` it into place only on success) is an acceptable alternative or complement if it more cleanly avoids partial-state exposure; either satisfies the followup.
  - Once a process acquires the lock, it must re-check `[[ -x "${WEASYPRINT_BIN}" ]]` before doing any install work — the other process may have finished the bootstrap while this one was waiting, in which case this process should just return success without redoing the install.
  - Decide (and document your decision inline as a comment) whether the losing process blocks/waits for the winner to finish (preferred: better UX, since a cold bootstrap is a rare, human-triggered, ~1-minute event anyway — see `src/cli/lib/ensure-weasyprint.sh`'s existing comments) or fails fast with a clear "another install is in progress, retry" message. Either is acceptable; a silent indefinite hang is not — bound any wait with a timeout.
  - Handle a stale lock (left behind by a process that was killed mid-bootstrap) so it doesn't permanently deadlock every future invocation. Model the remediation message on `ensure-weasyprint-fail()`'s existing pattern (it already prints a manual `rm -rf ... && python3 -m venv ...` remediation command on failure) — a stale-lock message should be similarly explicit about what to remove and why.
- **Critical ordering/trap interaction:** `ensure-weasyprint` is called at `src/cli/md2x.sh:116`, *before* that script creates `CSS_TMP_FILE` and conditionally registers its own `trap '...' EXIT` at lines ~216-235. A `trap ... EXIT` set inside `ensure-weasyprint()` (or `ensure-weasyprint.sh` at source time) would be silently overwritten by that later `trap` call, leaking the lock directory forever on every cold-bootstrap run. Release the lock synchronously on every exit path from `ensure-weasyprint()` — success, `ensure-weasyprint-fail()`'s `exit 2` paths, and any new failure path this task adds — rather than relying on a script-level `EXIT` trap that a later `trap` call would clobber. A function-local `trap ... RETURN` combined with explicit cleanup calls in `ensure-weasyprint-fail()` (which calls `exit` directly, bypassing `RETURN`) is one way to satisfy this; verify whichever mechanism you choose actually releases the lock on every path, including the pre-existing `ensure-weasyprint-fail()` exit paths.
- Preserve the existing warm-path behavior exactly: when `${WEASYPRINT_BIN}` is already executable, `ensure-weasyprint()` must still be a single, cheap `-x` test with no added lock-acquisition overhead — the existing docstring's "no other filesystem work... on essentially every invocation" claim must remain true. Only the cold path (the `-x` test failing) should touch the new locking machinery.
- Update `docs/architecture.md`'s "WeasyPrint bootstrap" subsection (`### WeasyPrint bootstrap`, under "Major components") to mention the new locking behavior, since it currently describes the cold-path sequence in enough prose detail that omitting the lock would leave it stale.
- Add test coverage proving the race is closed. The real bootstrap needs network access and is slow, so don't drive it for real. Instead:
  - Write a new, self-contained bats test file (e.g. `src/cli/test/bats/weasyprint-bootstrap-locking.bats`) with its **own** local `setup`/`teardown` — do not reuse the shared `md2x_setup` helper from `src/cli/test/helpers/common.bash` for this file's cases, and do not assume anything about task `006`'s changes to that helper (see `plan/overview.md`'s parallel-eligibility notes on the `001`/`006` interaction — that task changes `md2x_setup`'s default to pre-populate a working `weasyprint` binary, which would short-circuit the very cold-bootstrap code path this task needs to exercise). Follow `src/cli/test/bats/real-toolchain-e2e.bats`'s `e2e_setup`/`e2e_teardown` pattern as a model for a bats file that manages its own private working directory without depending on the shared stub-PATH helper's defaults.
  - In that dedicated setup, point `HOME` at a private per-case temp directory with **no** pre-existing `.md2x/venv`, and put a fast fake `python3` on `PATH` (ahead of the stub `pandoc`/`gs`/`pdftk` this file also needs) that fakes `-m venv <dir>` (creates `<dir>/bin/` and a nested fake `python3` inside it, with a deliberate short `sleep` to widen the race window), `-m ensurepip --upgrade` (no-op success), and `-m pip install ...` (creates `<dir>/bin/weasyprint` as an executable placeholder, another short `sleep` before it). Have the fake `python3`/`pip` steps append timestamped start/end markers to a shared log file the test controls.
  - Launch two concurrent PDF conversions against this environment (backgrounded `bin/md2x` invocations against a tiny fixture, `wait`-ed on) and assert: (a) both exit `0`; (b) the fake install steps' logged start/end intervals never overlap (proof the two never ran the venv-creation/pip-install sequence concurrently); (c) `${HOME}/.md2x/venv/bin/weasyprint` ends up executable exactly once (not corrupted/partially-overwritten).
  - This is the essential proof point; the exact log format and assertion mechanics are yours to design.
